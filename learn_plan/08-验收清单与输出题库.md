# 验收清单与输出题库

这份文件的作用是防止“看了很多，但没有真正掌握”。每个专题都必须产出可检查的输出，并且输出要有源码或测试证据。

## 总验收标准

你可以认为自己“掌握 Hermes harness 和核心 agent 工程”，至少要满足下面 8 条：

1. 能画出一轮 turn 的完整链路：输入、turn context、API messages、模型调用、工具调用、压缩、finalizer、session/memory 收尾。
2. 能解释 Hermes 的 harness 四件套：action space、observation、recovery、context budget。
3. 能判断一个新能力应该放到 core tool、toolset、plugin、MCP、skill，还是普通 CLI command。
4. 能解释 prompt caching 为什么是核心约束，以及哪些动态内容不能进入 system prompt。
5. 能解释 skills、memory、session search 的边界：过程记忆、声明式记忆、历史检索分别解决什么。
6. 能解释 Subagent/Multi-Agent 的预算、工具面、上下文继承、结果回传和并发限制。
7. 能解释超长程任务依赖哪些机制：iteration budget、context compression、SessionDB、background review、cron/kanban、恢复路径。
8. 能写出自己的迁移方案：如果做一个新 agent harness，哪些 Hermes 设计照搬，哪些不照搬，为什么。

## 证据规则

每个结论都要标注证据等级：

| 等级 | 含义 |
|---|---|
| A | 有源码位置 + 测试文件证明 |
| B | 有源码位置，但测试证据还没找到 |
| C | 只是推断或个人理解，必须标记为假设 |

不要写“应该是”“感觉是”当事实。写计划可以推测，写学习笔记必须证据化。

## 最终自测

闭卷回答下面 10 个问题。如果能回答 8 个，并且每个都有证据链，说明你已经不是“看过”，而是真的掌握了一大块。

1. Hermes 为什么把动态 recall context 注入 user message，而不是 system prompt？
2. 一个工具从 `registry.register()` 到模型调用，再到 result 回写，完整链路是什么？
3. 什么情况下工具可以并发执行，什么情况下必须顺序执行？
4. context compression 保护了哪些消息结构？
5. memory、session search、skill 的职责边界是什么？
6. `/learn` 到 `skill_manage` 到 `curator` 构成了怎样的自进化闭环？
7. subagent 如何被限制，避免无限分裂或抢占资源？
8. iteration budget、max_iterations、budget grace 分别解决什么？
9. background review 为什么需要特殊 tool restriction？
10. 如果你要给 Hermes 加一个新外部服务能力，应该用 core tool、plugin、MCP、skill 还是 CLI command？为什么？
